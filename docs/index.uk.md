# Курс: твій перший AI-агент

Вітаю на моєму навчальному курсі по створенню власного AI-агента.
Цей курс для тих, хто хоче вперше зрозуміти, як працює AI-агент, і написати
власні інструменти для нього.

В процесі навчання ми будемо рухатись «згори вниз»: спершу навчаємось користуватись
готовим агентом `tooled-ai-agent`, потім розбираємо, як він влаштований
всередині, розширюємо його і, нарешті, готуємо до реальних задач.

!!! important
    **Що потрібно знати:**

    - Основи Python (функції, класи, словники)
    - Роботу в терміналі (bash, Powershell)

!!! note
    **Як користуватися кодом уроків:** кожен урок має git-тег `lesson-NN`, який
    фіксує код на момент цього уроку. Найновіша версія завжди в `main`.

```bash
git checkout lesson-01    # код уроку 1
git checkout main         # повна версія
```

!!! warning
    `git checkout lesson-01` переводить репозиторій у стан detached HEAD.
    Якщо в папці є незакомічені зміни, збережіть їх на час перегляду уроку:

```bash
git stash          # прибрати зміни
git checkout lesson-01
# ... дивимось код уроку ...
git checkout main  # повернутися
git stash pop      # відновити свої зміни
```

!!! note
    Позначка **«Знадобиться далі»** показує, де інструмент чи прийом
    використовуватиметься в реальних агентах: Git-асистенті та SDD-фреймворку.

## Частина 1. Користувач

### [Урок 1. Встановлення і перший запуск](lessons/01-installation-and-first-run.uk.md) 🚧

**Мета:** встановити агента, підключити мовну модель і поставити перше питання.

- Встановлення на вашій платформі:
    - **Linux / macOS:** скрипти `install.sh` і `env.sh`
    - **Windows (рекомендовано):** WSL2 (`wsl --install`), далі як у Linux
    - **Windows без WSL:** команди Python у PowerShell (`python -m venv`, `pip install -e .`)
- Встановлення як звичайної програми через `pipx`
- Підключення моделі: безкоштовної (Ollama) або хмарної (Vertex AI, API-ключ)
- Перший запит
- Команди: `/help`, `/models`, `/model`, `/usage`, `/history`, `/search`

**Практика:** поставте агентові 3–4 питання, знайдіть одне з них через
`/search` і відкрийте збережену розмову у форматі `.md`.

### [Урок 2. Як агент спілкується з моделлю](lessons/02-how-the-agent-talks-to-the-model.uk.md) 🚧

**Мета:** зрозуміти, що відбувається під час одного звернення до моделі.

- Структура проєкту
- `config.toml`: звідки береться, як змінити, профілі моделей
- Виклик `completion()` і ролі повідомлень: `system`, `user`, `assistant`
- Токени, `temperature`, режим міркувань (thinking) і чому він впливає на швидкість
- Локальні й хмарні моделі: швидкість, якість, вартість

**Практика:** додайте свій профіль моделі, порівняйте відповіді двох моделей
на одне питання й різницю в `/usage`.

## Частина 2. Як працює агент

### [Урок 3. Інструменти (tool calling)](lessons/03-tools-tool-calling.uk.md) 🚧

**Мета:** зрозуміти, як модель «використовує» інструменти, не виконуючи код.

- Модель лише *просить* виклик функції, виконує його наш код
- Опис інструменту в JSON Schema
- Клас `Tool` і реєстр `ToolRegistry`
- Розбір інструменту `calculator`
- Чому опис кожного інструменту коштує токенів у *кожному* запиті
- Команда `/debug`: сирі запити й відповіді моделі

**Практика:** через `/debug` знайдіть момент, коли модель просить калькулятор,
і момент, коли отримує результат.

### [Урок 4. Агентний цикл](lessons/04-the-agent-loop.uk.md) 🚧

**Мета:** розібрати серце агента: цикл «модель → інструмент → модель».

- Метод `run()`, ліміт кроків `max_steps`
- `tool_call_id` і кілька викликів за один крок
- Помилки інструментів повертаються моделі
- Історія розмови як «пам'ять»: чому з кожним кроком ростуть токени, навіщо `/reset`

**Практика:** дайте агентові задачу на 3+ кроки й простежте в `/debug`, як росте
історія. Встановіть `max_steps = 1` і подивіться, що зміниться.

## Частина 3. Розширення

### [Урок 5. Свій перший інструмент](lessons/05-your-first-tool.uk.md) 🚧

**Мета:** написати власний інструмент і підключити його до агента.

- Інструмент `current_time` крок за кроком
- Чому опис (`description`) важливіший за код
- Результат інструменту читає модель, а не людина: короткий простий текст, без кольорів
- Тестування інструменту через `pytest`

**Практика:** напишіть самостійно `exchange_rate` (відкрите API НБУ)
або `get_weather` (Open-Meteo).

### [Урок 6. Читання файлів і пошук](lessons/06-reading-and-searching-files.uk.md) 🚧

**Мета:** навчити агента безпечно орієнтуватися у файлах проєкту.

- `list_files` (як `ls`), `read_file` (як `cat`)
- `find_files` — пошук файлів за шаблоном імені (як `find`)
- `search_files` — пошук тексту всередині файлів (як `grep -r`)
- Пісочниця: доступ лише до робочої папки (`safe_path`)
- Ліміти розміру, бінарні файли, ігноровані папки (`.git`, `.venv`)

**Знадобиться далі:** Git-асистенту — щоб розуміти код перед змінами;
SDD — щоб знаходити місця для реалізації задач.

**Практика:** попросіть агента знайти всі місця, де використовується `ToolRegistry`,
і пояснити, як влаштований `tooled-ai-agent`.

### [Урок 7. Зміна файлів, безпека і підтвердження](lessons/07-changing-files-safety-and-confirmation.uk.md) 🚧

**Мета:** дозволити агентові змінювати файли, зберігши контроль за собою.

- `write_file` — створити чи перезаписати файл
- `edit_file` — точкова заміна фрагмента замість перезапису всього файлу
- Підтвердження дій: показати diff і спитати `[y/n/d]`
- Скасування запиту (Ctrl+C) і відкат історії
- Prompt-ін'єкція: чому дані з файлів та інтернету — недовірений текст
- Docker-контейнер як пісочниця: агент бачить лише робочу папку
  і не може зіпсувати файли поза нею; запуск на будь-якій ОС

**Знадобиться далі:** механізм підтвердження — основа безпеки Git-асистента;
`edit_file` — головний інструмент виконання задач у SDD.

**Практика:** спробуйте «обдурити» агента через вміст файлу й переконайтеся,
що підтвердження вас захищає. Потім запустіть агента в контейнері
й перевірте, що файли поза робочою папкою йому недоступні.

### [Урок 8. Виконання команд і тестів](lessons/08-running-commands-and-tests.uk.md) 🚧

**Мета:** дати агентові запускати команди, не втрачаючи контролю.

- `run_command`: дозволений список команд, підтвердження, тайм-аут
- Обрізання довгого виводу: перші й останні рядки замість тисяч рядків
- `run_tests`: запуск `pytest` і короткий підсумок (скільки пройшло, що впало і чому)
- Маскування секретів: токени й паролі не повинні потрапити ні моделі,
  ні в архів сесій

**Знадобиться далі:** Git-асистенту — для git-команд і аналізу логів CI;
SDD — для перевірки кожної задачі тестами.

**Практика:** попросіть агента запустити тести проєкту, знайти причину падіння
(навмисно зламайте один тест) і запропонувати виправлення.

### [Урок 9. Системний промпт, профілі агентів і пам'ять](lessons/09-system-prompt-agent-profiles-and-memory.uk.md) 🚧

**Мета:** зробити з одного двигуна різних агентів.

- Як системний промпт змінює поведінку
- Профілі агентів `--agent`: свій промпт і свій набір інструментів
  (менше інструментів — менше токенів і менше помилок вибору)
- Довготривала пам'ять: інструменти `remember` / `recall`

**Практика:** створіть власний профіль, наприклад «перекладач» або
«рецензент коду» лише з потрібними йому інструментами.

### [Урок 10. Планування в агентному циклі](lessons/10-planning-inside-the-agent-loop.uk.md) 🚧

**Мета:** навчити агента не вгадувати, а уточнювати й планувати.

- `ask_user` — агент сам ставить уточнювальне питання посеред роботи
- `todo_add` / `todo_update` / `todo_list` — агент веде список задач
  і відмічає виконані, як це роблять агенти для коду
- Коли питати користувача, а коли вирішувати самому

**Знадобиться далі:** SDD — фаза уточнення вимог і список задач;
Git-асистенту — уточнення перед ризиковими діями.

**Практика:** дайте агентові розмите завдання («зроби інструмент для курсу валют»)
і подивіться, які питання він поставить і як розіб'є роботу на кроки.

## Частина 4. Підготовка до реальних задач

### [Урок 11. Надійність](lessons/11-reliability.uk.md) 🚧

**Мета:** агент не повинен «падати» чи зависати через збої моделі.

- Тайм-аут запиту замість нескінченного очікування
- Повтори при тимчасових помилках (мережа, перевантаження)
- Резервні моделі: коли ліміт вичерпано, перемкнутися на іншу (`litellm.Router`)
- Чому безкоштовні ліміти швидко закінчуються в агентному режимі

**Знадобиться далі:** обом агентам — довгі задачі не повинні зупинятися
через один збій.

**Практика:** налаштуйте ланцюжок резервних моделей і змоделюйте збій
основної (наприклад, неправильна назва моделі).

### [Урок 12. Ядро як бібліотека: події замість `print`](lessons/12-the-core-as-a-library-events-instead-of-print.uk.md) 🚧

**Мета:** відокремити логіку агента від інтерфейсу, щоб те саме ядро
працювало в терміналі, у вебі чи всередині іншого агента.

- Проблема: `Agent` сам друкує виклики інструментів і крутить спінер,
  тому його не можна використати без терміналу
- Обробники подій: `on_thinking`, `on_tool_call`, `on_tool_result`, `on_answer`, `on_error`
- Підтвердження дій як підключаємий обробник (`confirm`), а не `input()` всередині ядра
- `cli.py` як один з «підписників» подій
- Створення агента прямо з коду, без `cli.py` і без `config.toml`
- Публічний API пакета (`__all__`) і версіонування: що можна змінювати, а що ні

**Знадобиться далі:** Git-асистент і SDD-фреймворк будуть окремими проєктами,
які імпортують `tooled-ai-agent` як бібліотеку.

**Практика:** напишіть скрипт на 20–30 рядків, який створює агента з кодом,
дає йому задачу і записує всі виклики інструментів у файл, без жодного виводу на екран.

### [Урок 13. MCP: підключення готових серверів (клієнт)](lessons/13-mcp-connecting-ready-made-servers-client.uk.md) 🚧

**Мета:** дати агентові інструменти з будь-якого MCP-сервера.

- Що таке MCP і навіщо він потрібен: один протокол замість окремої
  інтеграції з кожним сервісом
- Архітектура: агент — клієнт, сервер надає інструменти (`tools/list`, `tools/call`)
- Транспорти: `stdio` (локальний процес) і HTTP (віддалений сервер)
- Обгортка `MCPTool(Tool)`: інструменти сервера реєструються поруч з власними
- Опис серверів у `config.toml` (`[mcp.servers.<ім'я>]`)
- Асинхронний SDK і синхронний агент: як їх поєднати
- Безпека: описи й результати чужого сервера — недовірений текст

**Знадобиться далі:** Git-асистенту — офіційні MCP-сервери GitHub і GitLab
замість написання власних інструментів для PR/MR та issues.

**Практика:** підключіть MCP-сервер файлової системи й порівняйте
його інструменти з власними `list_files` / `read_file`.

### [Урок 14. MCP: власний сервер](lessons/14-mcp-your-own-server.uk.md) 🚧

**Мета:** подивитися на протокол з іншого боку й зробити свої інструменти
доступними будь-яким MCP-клієнтам.

- MCP-сервер на Python за допомогою офіційного SDK (FastMCP)
- Інструмент на сервері — звичайна функція з типами й docstring
- Публікація існуючих інструментів `tooled-ai-agent` (`current_time`,
  `exchange_rate`) через MCP без переписування
- Перевірка сервера в MCP Inspector
- Підключення сервера до свого агента (урок 13) і до інших клієнтів,
  наприклад Claude Code чи VS Code

**Знадобиться далі:** інструменти, які ви напишете для Git-асистента,
зможуть використовувати й інші агенти.

**Практика:** зробіть MCP-сервер з інструментом `exchange_rate` і викличте його
з двох різних клієнтів.

### [Урок 15. Фінальний проєкт: Git-агент](lessons/15-final-project-a-git-agent.uk.md) 🚧

**Мета:** зібрати з вивченого агента для реальної задачі.

- Профіль `--agent git` зі своїм промптом і набором інструментів
- `git_status`, `git_diff`, `git_log` — лише читання, без підтверджень
- `git_commit` — з показом diff і підтвердженням
- Повторне використання: файлові інструменти, `run_command`, `run_tests`,
  маскування секретів, `ask_user`
- Що далі: як із цього вирости в окремий Git-асистент (GitHub/GitLab, CI)
  і SDD-фреймворк на основі ядра `tooled-ai-agent`

**Практика:** попросіть агента переглянути ваші незакомічені зміни,
запустити тести й запропонувати повідомлення коміту.
